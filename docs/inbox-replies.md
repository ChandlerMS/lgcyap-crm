# Inbox conversations and editing

The Inbox card below the recruiting pipeline previews active HubSpot conversations on hover or keyboard focus. Each row's Open button reads that conversation and shows a plain-text reply composer inside the floating preview. Card links use the canonical `#inbox/thread/<id>` route. The preview uses the available viewport height, with a separately scrolling message history and the reply composer kept in view. The previous `#inbox/<id>` route was not recognized and fell back to Dashboard.

The Inbox preview starts compact and expands vertically only when Open selects a conversation. Hover previews close when the pointer leaves the title and popup, including while a reply field has focus. Closing an Inbox preview returns it to the compact conversation list. Drafts and pending-send state are retained per conversation when the preview closes. Drafts and uncertain-send blocks are retained per conversation when returning to the list. Sending requires an explicit Send reply click. Message history remains available independently of reply permission.

`POST /api/inbox-reply` supports `prepare` and `send`. Both require the CRM session, editor authorization, same-origin JSON requests and the existing production write capability. The server verifies private app `59264745` in HubSpot portal `50894788`, with `conversations.read`, `conversations.write` and `crm.objects.owners.read`. The employee's exact sign-in email must resolve to one active HubSpot owner's `userId`; the sender is that user's `A-` actor, never the owner ID or a browser-provided identity.

The server derives recipients, channel and channel account from the latest nonarchived MESSAGE. Supported channels are HubSpot live chat (1000), Messenger (1001) and email (1002). Other channels, including WhatsApp, require the native HubSpot interface. Preparation returns ten-minute signed reply details bound to the employee and current conversation. Send re-reads those details before POSTing. A changed message, recipient, channel or expired signature requires review of refreshed reply details. The existing metadata-only Postgres ledger prevents duplicate requests; no message body or address is written to it. Network ambiguity or failed acknowledgement blocks automatic resends and preserves the draft for checking in HubSpot. The guarantee is per request ID: navigating away from the dashboard clears drafts; manually composing a new reply afterward is a new operation. Demo mode hides live conversations, and pending-send state survives live/demo switches.

API reference: [HubSpot Conversations guide](https://developers.hubspot.com/docs/api-reference/conversations-conversations-v3/guide), [send a message](https://developers.hubspot.com/docs/api-reference/conversations-conversations-v3/public-message/post-conversations-v3-conversations-threads-threadId-messages), and [message sorting](https://developers.hubspot.com/docs/api-reference/conversations-conversations-v3/public-message/get-conversations-v3-conversations-threads-threadId-messages).

## Full Inbox and bidirectional changes

Both the dashboard Inbox preview and full Inbox page use the same reply composer and guarded reply endpoint. Each surface retains drafts per thread while switching conversations. Replies write directly to the existing HubSpot thread; HubSpot remains the source of truth. Completed message and conversation reads refresh every minute while visible and when the browser window regains focus. Paused or incomplete pagination walks remain under the user's Continue/Refresh controls. History and status refreshes preserve drafts.

Conversation controls use `POST /api/inbox-thread` to prepare a signed snapshot and close/reopen a thread or restore an archived thread. The same production editor, session, origin, credential, and conversations read/write checks apply. Only `status` or `archived:false` is sent to HubSpot. No deletes or reassignment are performed. The snapshot binds the employee, credential, current status, archive state, assignee, and latest-message timestamp. Changed or expired context stops the edit. A metadata-only ledger records intent before the write and prevents automatic replay after ambiguous outcomes. HubSpot does not offer conditional writes for these edits, so a small race remains between the final read and the update.

New message actions appear in the dashboard card/preview and full page. They explicitly open HubSpot's native Inbox in a new tab; choose Compose there to start a new conversation. The public Conversations API sends messages to existing threads and does not offer a native-email thread creation endpoint or editing of already-sent message bodies. We do not substitute a CRM email log for an actually sent Inbox message. Attachments, unsupported channels, reassignment, and other native capabilities remain in HubSpot.

The thread controls need the same existing `conversations.read`, `conversations.write`, and `crm.objects.owners.read` private-app access as replies. No messages are sent as part of development or deployment verification.

Reference: [update a thread](https://developers.hubspot.com/docs/api-reference/conversations-conversations-v3/public-thread/patch-conversations-v3-conversations-threads-threadId), [Conversations API](https://developers.hubspot.com/docs/api-reference/latest/conversations/conversations/guide), and [new-thread limitation](https://community.hubspot.com/t5/APIs-Integrations/Custom-Channel-send-email-and-create-a-ticket-through-API/m-p/1234143).
